# Code metrics generation

The code metrics were generated through an AI-assisted analysis process. Sprint 2 and Sprint 3 are understood to have used a similar process. For Sprint 4, OpenAI Codex generated the tools in `tools/`, the metrics CSV, the summary CSV, and the graph. Microsoft's code analysis engine calculated the Sprint 4 numeric metrics through that tooling. The existing Sprint 2 and Sprint 3 CSVs were retained unchanged.

`tools/Program.cs` uses `Microsoft.CodeAnalysis.Metrics` 5.6.0 (Roslyn 4.12) to analyze the C# source in `terraria` and `MonoGameLibrary`. It compiles the source in memory using C# 13, Debug preprocessor symbols, cached .NET 9 reference assemblies, and the MonoGame assembly. The game compilation also references the library compilation. It excludes `bin` and `obj` directories and stops if compilation errors are found. This approach calls the analysis API directly because the package's command-line launcher could not discover MSBuild on this Mac.

The tool calls `CodeAnalysisMetricData.ComputeAsync` and exports the engine's maintainability index, cyclomatic complexity, inheritance depth, coupled-type count, source lines, and estimated executable lines for each type and member, including property accessors. `CodeMetricsSprint4.csv` follows the previous CSVs' column format.

`tools/plot_metrics.py` reads the sprint CSVs and creates `CodeMetricsSummary.csv` and `CodeMetricsTrends.svg`. It separates game and library code, treating the historical `sprint2` project as the game project. It calculates unweighted averages of Type rows for all metrics except inheritance depth, where it uses the maximum. Member rows are excluded from these calculations. Nested type source spans can overlap their containing types, so average source lines do not represent unique file-line totals. Although the earlier sprints used a similar process, their exports do not record the exact analyzer versions or settings, so identical measurement configurations across sprints have not been verified.
